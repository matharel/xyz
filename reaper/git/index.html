Reaper Git Workflow

This is a compact, practical wiki that explains a beginner-friendly but robust workflow for backing up and versioning your Reaper projects at the album level (one git repo that contains multiple song folders). It focuses on the things you asked about: when to commit and how to write commit messages, how to version mix iterations, and whether/how to use branches.

Context / assumptions

  • You keep one Git repo per album (e.g. This super Band/).
  • You do not commit audio files (audio/ folders are ignored). Git tracks .RPP and other small project metadata.
  • You use rsnapshot or a separate backup for actual audio files and big exports.

Goals of this workflow

  • Keep a tidy, meaningful history of changes to .RPP files.
  • Make it easy to reproduce a particular mix/export by linking it to a Git commit or tag.
  • Keep collaboration safe and simple (avoid heavy branching complexity unless needed).
  • Use Git tags and small conventions to mark important milestones (mix proposals, approved versions, masters).

When to commit and how

When to commit (practical rules)

  • Start of a session: commit before you begin (“session start: recording day 2025-10-02”).
  • After major structural edits: arrangement changes, major track adds/removes, large routing changes.
  • Before/after editing: after comping takes / fixing takes / vocal comp.
  • Before each mix pass: commit the .RPP used to export a mix.
  • When you reach a named milestone: e.g. “edited version complete”, “mix v1 ready for review”.
  • End of session: quick commit with a note of what you did.

Aim for small, meaningful commits: each commit should answer “what changed and why”.

Commit message structure (simple, consistent)

Use a short header line (<=72 chars), then an optional body with more details. A structured prefix helps scanning history.

Suggested template:

<type>(<scope>): short summary

Detailed notes (why, author notes, timestamp, export filename, etc.)

Markers: [session: YYYY-MM-DD hh:mm] [export: filename.wav]

Recommended type prefixes (pick a small set you like):

  • session — general session start/end notes
  • arr or arrangement — structural / arrangement edits
  • edit — comping / edit / cleanup
  • mix — mixing changes
  • fix — bugfix / routing error / lost plugin
  • doc — README, notes, metadata

Examples

mix: mix v1 - flat export after recording

Notes: quick flat mix to check balance. Needs brighter snare, less vocal reverb.
[session: 2025-10-02 18:03] [export: my-great-song-mix-v1-flat.wav]

edit: complete vocal comp for verse 1 and 2

Removed noisy breaths, tightened timing ~30-50ms. Markers: V1_comped [session:
2025-10-02 20:40]

Why include these details?

  • They make it trivial later to know which commit produced a specific exported mix.
  • They help collaborators find the exact .RPP used for an export.

Versioning mixes: conventions

You asked whether to duplicate .RPP files or to rely on git labels and exports. The cleanest approach is to not duplicate .RPP files as a primary strategy. Instead use a combination of git commits, tags, and exported filenames.

Core idea

  • Keep working .RPP as the single source of truth.
  • When you export a mix (WAV/MP3), record the export filename in the commit message and create a git tag that identifies that exported mix version.
  • Optionally attach the exported file to a GitHub Release (or store it via rsnapshot) — but do not commit large audio into the repo.

Naming conventions (consistent & human-friendly)

Pick a small, consistent scheme for labeling mix iterations. Example convention that scales well:

  • session-flat — immediate mixes right after recording (flat / no fancy processing)
  • edited — editing/comping finished
  • mix-v1, mix-v2, … — iterative mix proposals (major changes to artistic direction)
  • mix-v2.1, mix-v2.2 — micro iterations: detail passes (EQ tweaks, automation)
  • mix-v2-final or mix-v2-approved — the band accepted the artistic direction
  • master-v1 — final mastered export

Filename examples for exports

my-great-song_session-flat_2025-10-02.wav
my-great-song_edited_2025-10-03.rpp
my-great-song_mix-v1_2025-10-05.wav
my-great-song_mix-v2_2025-10-15.wav
my-great-song_mix-v2.1_detailpass_2025-10-17.wav
my-great-song_mix-v2-approved_2025-10-18.wav
my-great-song_master-v1_2025-10-20.wav

Why include the date? It avoids ambiguity when you have many exports.

Using Git tags to label mix exports (recommended)

When you export a mix and commit the .RPP used to create it, create an annotated tag that points to that commit. Annotated tags can carry a message.

Example:

# commit the RPP with a descriptive message first
git add my-great-song/my-great-song.RPP
git commit -m "mix: mix-v2 - direction approved by band [export: my-great-song_mix-v2_2025-10-15.wav]"
# create an annotated tag
git tag -a my-great-song-mix-v2 -m "Mix v2 approved by band — export: my-great-song_mix-v2_2025-10-15.wav"
# push branch and tags
git push origin main
git push origin my-great-song-mix-v2
# or push all tags
git push --tags

Tags are perfect because they point to the exact commit (the exact .RPP) used to make the export. Later, checking out that tag reproduces the project state exactly.

On GitHub: create a Release using that tag and upload the exported WAV as the release asset. Your repo stays small but your release stores the audible artifact.

When (if ever) to duplicate .RPP files

  • Use duplication only if you want to keep multiple states easily accessible inside the tree (e.g. finals/my-great-song-mix-v2.rpp). This is redundant with tags but has the benefit of being visible in the file tree.
  • If you do use a finals/ folder, make sure the filename clearly states the version: finals/my-great-song_mix-v2_2025-10-15.rpp
  • Personally, I recommend tags + export naming over duplicating .RPP files — duplication clutters the tree and can lead to divergence.

Branching — when and how

You said you use Git regularly but are not at ease with branching. Keep the branching model very simple.

Minimal branching model (recommended)

  • main (or master) — canonical working project. This branch contains the current working .RPP and history.
  • Use branches only for experiments or parallel, major alternate directions.

When to create a branch:

  • You want to try a very different artistic direction that you may discard (e.g. a heavy synth arrangement replacing guitars).
  • You want to test destructive editing or radical changes that you don’t want to mix into main immediately.

Example branch naming

  • mix/proposal-v2 — a branch containing a different mix approach.
  • arrangement/add-bridge — rearrangement experiment.

Simple branching workflow (step-by-step)

  1. Create a branch from main:
# create and switch
git checkout -b mix/proposal-v2
  1. Work in Reaper, save .RPP, commit locally:
git add my-great-song/my-great-song.RPP
git commit -m "mix(proposal): big reverb change + vocal comp for testing"
  1. If you like the branch and want to merge it into main:
git checkout main
git merge --no-ff mix/proposal-v2 -m "merge: mix/proposal-v2 — accept new direction"
# push
git push origin main
  1. If you decide to discard the branch:
git branch -d mix/proposal-v2  # local delete
# if pushed
git push origin --delete mix/proposal-v2

Notes about conflicts

  • Because .RPP is text, Git will attempt to merge. If two people changed the same area of the .RPP it can produce conflicts. Resolve them by opening both versions in a text editor or by creating separate exports and deciding which one to keep.
  • If you expect multiple people to edit the same .RPP concurrently a lot, consider a locking policy (person announces they will edit the song) or using Git LFS file locking for binary blobs (not helpful for .RPP but relevant for large files).

Branch flow for a typical mix lifecycle

If you prefer branches for each major mix version, you can use a pattern like:

  • main — base project
  • mix/v1 — first official mix pass (branch created from main)
  • mix/v2 — created if you need a radical remake

Once a mix/vX is approved, merge back to main and tag it.

But again: you don’t need to branch for every tiny mix iteration — tags + commits + export naming are usually enough.

Example concrete workflow (end-to-end)

  1. Session start
# commit the RPP before starting
git add my-great-song/my-great-song.RPP
git commit -m "session: start recording day 2025-10-02 - drum basic take"
git push
  1. After editing and comping
git add my-great-song/my-great-song.RPP
git commit -m "edit: comped vocals, removed noisy breaths from verses [session: 2025-10-03]"
git push
  1. Flat mix after session (quick check)
  • Export my-great-song_session-flat_2025-10-03.wav using Reaper.
  • Commit the .RPP you used and tag it:
git add my-great-song/my-great-song.RPP
git commit -m "mix: session-flat export for balance check [export: my-great-song_session-flat_2025-10-03.wav]"
git tag -a my-great-song-session-flat-2025-10-03 -m "Session flat — quick balance check"
git push && git push --tags
  1. First mixing pass (mix-v1)
  • Work on main or create mix/v1 branch if you prefer.
  • When you export a candidate mix my-great-song_mix-v1_2025-10-05.wav, commit the .RPP and tag:
git add my-great-song/my-great-song.RPP
git commit -m "mix: mix-v1 — initial mix proposal [export: my-great-song_mix-v1_2025-10-05.wav]"
git tag -a my-great-song-mix-v1 -m "Mix v1 - initial artistic direction"
git push && git push --tags
  1. Band rejects the direction — create mix/v2 branch and try a different approach
git checkout -b mix/v2
# work, commit locally many times
git add ... && git commit -m "mix(proposal): darker tone, synth pad in chorus"
# when ready, push branch
git push -u origin mix/v2
  1. Band approves mix/v2 (now detail passes)
  • Make detail commits like mix: mix-v2.1 - automation and vocal delay fixes.
  • Export my-great-song_mix-v2.1_2025-10-17.wav
  • Commit and tag my-great-song-mix-v2.1 (or tag the final mix-v2-approved)
  1. Master
  • After mastering, make a master-v1 commit and tag. Upload final WAV to GitHub Release for that tag or move final master to your audio backup solution.

Cheat-sheet: useful git commands

# basic commits
git add path/to/file
git commit -m "type: short summary\n\nmore details"

# branching
git checkout -b my-branch
git checkout main
git merge my-branch
git branch -d my-branch

# tagging (annotated tag)
git tag -a my-tag -m "message"
git push origin main
git push --tags

# show history
git log --oneline --graph --decorate

# check out a tag (detached HEAD)
git checkout my-tag
# or create branch from tag
git checkout -b window-from-tag my-tag

Extras & tips

  • Storing exported WAVs: keep them in rsnapshot or upload them to GitHub releases tied to tags. This keeps your .git small.
  • If you really want final RPP copies: store them in finals/ with clear filenames (e.g. finals/my-great-song_mix-v2_2025-10-15.rpp). But tags are usually enough.
  • Make commit messages actionable: treat them as short notes you’d like to read six months later.
  • Automation: consider a small scripts/release-mix.sh that commits, tags, and creates a draft GitHub release (you can use gh CLI).
  • Backups: your rsnapshot keeps all audio; pushing the repo ensures the .RPP metadata is off-site.

scripts/release-mix.sh (what it does)

  • Commits the current .RPP for a specified song (if there are changes).
  • Creates an annotated tag with a consistent name that includes the song and the mix version.
  • Optionally prints the gh CLI commands you can run to create a GitHub Release and upload the exported WAV file as a release asset (the script does not call gh by default — uncomment if you want automation).

Note: the script is intentionally conservative about pushing or uploading assets automatically; it focuses on producing a predictable commit + tag so you can attach exported WAVs to releases yourself or automate later.
