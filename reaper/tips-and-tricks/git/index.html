REAPER config tree — file-by-file guide (loose-mode oriented)

Directories

AutomationItems/

Purpose: Stores per-project automation item data and snapshots.
Keep? Optional → Yes if you want project automation preserved; No if you treat automation data as ephemeral.
Why / Notes: Usually small. If you want exact project-state portability, keep it; otherwise safe to ignore.

ColorThemes/

Purpose: REAPER color theme files (.ReaperThemeZip / theme files).
Keep? Yes
Why / Notes: Small, purely cosmetic, useful to restore UI look.

Cursors/

Purpose: Custom mouse cursors (rare).
Keep? Optional
Why / Notes: Keep if you customized cursors; otherwise ignore.

Data/

Purpose: Misc data used by REAPER or extensions; contents vary.
Keep? Optional → inspect contents.
Why / Notes: Some items may be caches; check before committing. If it contains generated cache, prefer ignoring.

Effects/

Purpose: Local FX preset files / effect-related data.
Keep? Yes (but inspect)
Why / Notes: Often useful for consistent FX presets. If it holds large binary plugin data, reconsider.

FXChains/

Purpose: Saved FX chain files (your presets / chains).
Keep? Yes
Why / Notes: Valuable to restore saved chains.

KeyMaps/

Purpose: MIDI/OSC keymaps and controller mappings.
Keep? Yes
Why / Notes: Critical if you rely on controller mappings.

LangPack/

Purpose: Language pack files.
Keep? Optional — Yes if you use a custom language pack.
Why / Notes: Otherwise not needed.

MIDINoteNames/

Purpose: MIDI note name customizations.
Keep? Optional → Yes if you changed note names.
Why / Notes: Small and harmless.

MetadataCaches/

Purpose: Caches for file metadata (project lists, media).
Keep? No (ignore)
Why / Notes: Cache; regenerated by REAPER. Saves space and avoids noisy commits.

MouseMaps/

Purpose: Mouse action maps.
Keep? Yes if you have custom mouse maps.
Why / Notes: Small and useful.

OSC/

Purpose: OSC remote control mappings.
Keep? Yes if you use OSC; otherwise optional.
Why / Notes: Useful to keep for reproducing remote control setup.

ProjectTemplates/

Purpose: Saved project templates (.rpp templates).
Keep? Yes
Why / Notes: Important for reproducible sessions.

QueuedRenders/

Purpose: Metadata for queued renders.
Keep? Optional / No
Why / Notes: Usually ephemeral; safe to ignore unless you want queued renders preserved.

ReaImGui/

Purpose: Data for ReaImGui extension (GUI assets & resources used by scripts).
Keep? Optional → Yes if you rely on local ReaImGui GUI resources.
Why / Notes: Can be kept but inspect size.

ReaPack/

Purpose: ReaPack-managed data and maybe caches/packages.
Keep? No for the folder contents; Yes for ReaPack config files (reapack.ini) — see files section.
Why / Notes: ReaPack-installed scripts are best reinstalled via ReaPack (keep the repo list instead of vendorizing everything). If you do vendor them, be deliberate.

Scripts/

Purpose: All user scripts (Lua, EEL, Python) and script folders.
Keep? Yes, but be selective.
Why / Notes: Keep your own Scripts/seb/ dev scripts. For ReaPack-managed script folders, prefer not to commit full third-party packages (track repo list instead). Suggest: commit Scripts/seb/, optionally Scripts/README.md.

TrackTemplates/

Purpose: Track template files.
Keep? Yes
Why / Notes: Useful and small.

UserPlugins/

Purpose: Third-party plugin .dll / .so files or local plugin data (e.g., SWS .so).
Keep? Optional → No for binaries, Yes for tiny helper configs.
Why / Notes: Binary plugins are system/OS-specific (and usually installed separately). Don’t vendor big binaries into config repo — reinstall / package manager handles them. If you have small local helper files (like .ini for a local plugin), consider keeping those separately.

presets/

Purpose: Generic presets (various plugins / settings).
Keep? Yes if they are user presets you made.
Why / Notes: Useful to restore presets.

reaper_www_root/

Purpose: Local web root for REAPER web UI / resources (rare).
Keep? Optional
Why / Notes: Keep if you customised it; otherwise ignore.

trash/

Purpose: Reaper’s internal trash/backup area.
Keep? No
Why / Notes: Ephemeral; ignore.

Files (top-level .ini and others)

General rule for your loose mode: keep user preferences that you personally tweaked (reaper-kb.ini, reaper-menu.ini, reaper-themeconfig.ini, project templates, keymaps, color themes). Avoid large caches, plugin-scan lists, undo logs and registration/license files (privacy & portability).

BR.ini

Purpose: SWS / BR (Breeder) extension config file (if you use BR/SWS scripts).
Keep? Yes if you use BR/SWS features.
Why / Notes: Small and useful.

README.md

Purpose: Repo documentation.
Keep? Yes
Why / Notes: Good place to explain your setup.

S&M.ini

Purpose: SWS/S&M extension config (SWS actions/macros).
Keep? Yes if you use SWS S&M features.
Why / Notes: Useful to reproduce SWS/S&M configuration.

SWS-RenamePresets.txt

Purpose: Text file listing SWS rename presets (SWS extension).
Keep? Yes if that’s your custom data.
Why / Notes: Small and useful.

reapack.ini

Purpose: ReaPack settings (repositories subscribed, package meta).
Keep? Yes (important)
Why / Notes: Track this so on reinstall you can re-subscribe to the same ReaPack repos.

reaper-clap-linux-x86_64.ini

Purpose: Platform/plugin-specific config for CLAP plugin host or plugin wrapper.
Keep? Optional → Yes if relevant to your system.
Why / Notes: Machine-specific; keep if you rely on it.

reaper-defpresets.ini

Purpose: Default presets registry.
Keep? Optional → Yes if you rely on customized defaults.
Why / Notes: Small; safe to keep.

reaper-extstate.ini

Purpose: Extensions’ saved state (SWS / scripts / extension preferences).
Keep? Optional → Usually NO for loose-mode (can be noisy).
Why / Notes: Often contains volatile state; keeping it may cause noisy commits. Only keep if you need exact extension state restored.

reaper-fxtags.ini

Purpose: FX tagging metadata (organizing plugins).
Keep? Yes if you used FX tags.
Why / Notes: Small and helpful for organizing plugins.

reaper-install-rev.txt

Purpose: Text file with REAPER install revision/version.
Keep? Optional → Yes (tiny).
Why / Notes: Handy for tracking which REAPER build you used.

reaper-jsfx.ini

Purpose: JSFX (built-in effects) settings / registry.
Keep? Optional → Yes if you heavily customise JSFX settings; otherwise optional.
Why / Notes: Not usually huge; keeping restores JSFX state.

reaper-kb.ini

Purpose: Keyboard shortcuts (keymap).
Keep? YES — track
Why / Notes: Essential. Commit this.

reaper-menu.ini

Purpose: Custom menu sets & actions.
Keep? YES — track
Why / Notes: Essential for your custom menus.

reaper-midihw-alsa.ini & reaper-midihw-linux.ini

Purpose: MIDI hardware settings (ALSA/Linux).
Keep? Optional → Yes if you want to restore MIDI device keying, but note device names can change between machines.
Why / Notes: Good to keep for same machine; consider editing if you move between hosts.

reaper-mouse.ini

Purpose: Mouse mapping preferences.
Keep? Yes if you customized them.
Why / Notes: Small and useful.

reaper-recentfx.ini

Purpose: Recently used FX lists (runtime history).
Keep? No (ignore)
Why / Notes: Noisy and ephemeral.

reaper-reginfo2.ini

Purpose: Registration/installation info and possibly path data.
Keep? No (do not commit to public repo)
Why / Notes: May contain registration keys or machine-specific info — treat as sensitive. Exclude from repo or keep locally but out of version control.

reaper-render.ini & reaper-render2.ini

Purpose: Render presets and queued render settings.
Keep? Yes if you want to preserve render presets/queues.
Why / Notes: Handy for reproducible exports.

reaper-themeconfig.ini

Purpose: Theme & toolbar layout configuration.
Keep? Yes
Why / Notes: Restores UI layout and theme choices.

reaper-vstplugins64.ini

Purpose: List/scan results of VST plugins (64-bit).
Keep? No (ignore)
Why / Notes: Machine- and path-specific; plugin paths differ across systems and can be large/noisy. Re-scan on new machine. If you do want to track plugin list for exact reproduce, keep it privately — but generally exclude.

reaper-wndpos.ini

Purpose: Saved window positions (layouts).
Keep? Optional → Yes if you want exact window placement restored.
Why / Notes: May be machine/display-specific (multi-monitor differences).

reaper.ini

Purpose: Global REAPER preferences (audio device settings, many UI / behaviour prefs).
Keep? Yes (but with caution)
Why / Notes: This is the big one — contains many UI and behaviour tweaks you want in loose mode. However it can also contain machine-specific audio device names, paths, or sensitive data. Before committing: scan it for absolute paths, audio device names, or registration info and decide whether to keep or scrub those lines. Consider adding /reaper.ini to .gitignore if you plan to use repo across different machines, or keep it and be careful.

sws-autocoloricon.ini

Purpose: SWS extension autocolor/icon settings.
Keep? Yes if you use SWS and want consistent icons/colors.
Why / Notes: Small and useful.

Quick summary / suggested .gitignore patterns (loose-mode friendly)

If you want a quick .gitignore starting point tuned to the above recommendations:

# generated / cache / trash
MetadataCaches/
trash/
QueuedRenders/
reaper-recentfx*.ini
reaper-vstplugins*.ini
reaper-extstate.ini
reaper-reginfo2.ini
reapeaks/
Undo_Buf/

# plugin caches / bad scan logs
reaper-vstplugins*-bad.ini

# logs & backups
*.log
*.rpp-bak
*.rpp-undo

Notes: keep reaper-kb.ini, reaper-menu.ini, ColorThemes/, TrackTemplates/, FXChains/, Scripts/ (your own), KeyMaps/, reaper-themeconfig.ini, reaper-render*.ini, reapack.ini, BR.ini, S&M.ini, etc.

Final tips

  • Sensitive files: reaper-reginfo2.ini and any license files should not be pushed to public repos. Keep them out of version control or in a private location.
  • Binaries: avoid committing plugin .so/.dll in UserPlugins/; install via package manager or keep a separate binary backup.
  • Scripts: keep your scripts (Scripts/seb/) in the repo. For ReaPack-managed scripts, track reapack.ini (so you can re-sync) rather than large vendorized copies.
  • Check before commit: do git status and git diff after initial git add to make sure nothing unexpected (big caches, binary blobs) slipped in.
