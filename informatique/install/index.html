dBus Desktop Bus

Permet de passer des messages entre applications (Inter-Process Communication system), par exemple :

  • udisks permet d’intéragir avec les périphériques de stockage
  • networkmanager gère les connexions réseaux
  • pipewire audio and video routing between different pieces of software

Les messages entre les membres de dBus passent par un bus.

Il y a deux bus:

  • le bus système: celui de la machine. Les daemons y sont connectés pour différents services (montage de disque, heure du système, hostname)
  • le bus session: chaque session ouvre un bus différent. Les services appartenant à l’utilisateur y sont connectés (notifications, pipewire, clipboard manager …)

A session bus is a single dbus-daemon process per graphical or login session; client processs connect to it via the environment variable DBUS_SESSION_BUS_ADDRESS. Ifthat env var isn’t set for a process, that process won’t find the session bus and therefore can’t talk to user services on it.

It’s the display/login manater that sets up the graphical session and the session bus.

[https://www.baeldung.com/linux/dbus](What Is DBus Practically Useful For? | Baeldung on Linux) [https://www.linuxembedded.fr/2015/07/comprendre-dbus](Comprendre dbus | Linux Embedded)

systemd

systemd is the first program that runs when Linux boots.

Its main job is to start and supervise everything else: from low-level system services (like networking, logging, sound servers) to per-user background programs. Unlike older init systems that just launched things and forgot about them, systemd keeps track of all programs, can restart them if they crash, and organizes them into units (like Lego blocks) with clear rules about who depends on whom.

Why this matters:

  • Think of systemd as the orchestra conductor:
    • It tells “violins first, then brass” → e.g. “start udev before networkd”.
    • It makes sure if one instrument/player (a daemon) stops, it can restart it.
    • It knows which players belong to which section → uses cgroups to group processes.
  • For you as a user:
    • When you type systemctl start pipewire –user, you’re asking your personal systemd to run PipeWire in your session.
    • When you type systemctl status sshd, you’re asking the system systemd (PID 1) about the SSH daemon.

Systemd and D-Bus are tightly integrated. systemd manages lifecycle + resources, D-Bus provides communication and activation.

Polkit

Polkit (short for PolicyKit) is like a permission manager for Linux.

  • It decides who is allowed to do what on the system.
  • It runs quietly in the background as a system service (polkitd).
  • It doesn’t ask for passwords itself — it just checks policies. When something needs your permission, it asks an authentication agent (like polkit-gnome) to show you a prompt.

polkit is the system’s “permission manager” for administrative actions.

polkit-gnome is the helper that politely asks the user when their approval is needed. Together, they let normal users safely perform privileged actions in a graphical desktop, without giving full root access to everything.

Polkit Authentifcation agent

polkit-gnome is a small background program called an authentication agent. It doesn’t do anything visible most of the time — it just waits quietly in the background.

Then, when a graphical application (or a background service) tries to do something that requires admin rights (like root privileges), it pops up a password dialog that asks for your confirmation or password.

It’s basically the bridge between system permissions and your desktop environment.

Think of Linux desktop permissions as a conversation:

RoleExample
App“Hey, I want to mount this encrypted drive!”
polkitd (system daemon)“That’s a privileged action — who’s asking?”
polkit-gnome (the agent)“It’s the user in this graphical session — I’ll ask them for permission.”
YouYou type your password or click “Allow.”
polkit-gnome → polkitd“The user approved this, go ahead.”
App“Thanks, operation complete.” ✅

Without an agent, polkitd has no way to ask you — so the operation just silently fails (like your USB case earlier). Usage examples:

  • udiskie trying to mount or unlock a USB drive or encrypted partition
  • gparted formatting or partitioning disks
  • changing system-wide PipeWire or PulseAudio settings
  • authorizing a Bluetooth pairing or file transfer

polkit-gnome is the lightweight “password prompt” helper for your graphical session. When a GUI program needs admin permission — to mount, unlock, configure, install, or connect something — polkit-gnome is what politely asks you:

Unified Kernel Image

A Unified Kernel Image (UKI) is a single file that bundles together everything your system needs to boot:

  • The Linux kernel
  • The initramfs
  • The kernel command line
  • Optionally, the firmware and bootloader stub (for example, systemd-stub)

It’s usually stored in:

/efi/EFI/Linux/arch-linux.efi

In contrast, the classic setup keeps these as separate files:

/boot/vmlinuz-linux          ← the kernel
/boot/initramfs-linux.img    ← the initramfs

and the bootloader (GRUB, systemd-boot, etc.) reads them separately. It’s cleaner, especially with systemd-boot but requires relatively modern firmware.

Systemd

Login and launching Wayland compositor

greetd will manage the login:

#/etc/greetd/config.toml
vt = 1
[default_session]
command = "tuigreet --remember --remember-session --session-wrapper compositor-wrapper"
user = "greeter"
  • --remember last user
  • --rembember-session remember last session
  • --session-wrapper: specify a wrapper command to execute. This command receive the session command as its arguments

The Wayland sessions are in /usr/share/wayland-sessions, here is sway.desktop:

[Desktop Entry]
Name=Sway
Comment=An i3-compatible Wayland compositor
Exec=/usr/bin/sway
Type=Application
DesktopNames=sway;wlroots

So the session-wrapper will execute the script compositor-wrapper and pass it the argument of the session exec, here it will be /usr/bin/sway.

Let’s look at the wrapper command that we put in /usr/local/bin/compositor-wrapper:

source "$HOME/.config/env/compositor"

# exec systemd-cat -t compositor "$@" → with this version, sway output go to systemd journal
exec "$@"

This wrapper script source our compositor variables and then exec the compositor passed as an argument.

Automatic backup with a systemd timer

  1. wrapper script rclone-koofr-sync contains the backup command
  2. systemd service rclone-koofr-sync.service to run the script
  3. systemd timer rclone-koofr-sync.timer that triggers the service once a week.
  4. journalctl --user -u rclone-koofr-sync.service show each sync’s progress and errors.

for ch in "a" "1" "" "" "" "😀" "汉"; do
    code=$(printf '%x' "'$ch")
    font=$(fc-match -s ":charset=$code" | head -n1)
    printf "%s (U+%s) → %s\n" "$ch" "$code" "$font"
done
